# 0034 · The infrastructure is set up in the browser

Status: accepted · 2026-11-06 · Changes ADR 0033 (where the six services are set)

## Context

ADR 0033 set PostgreSQL, Valkey, S3, OpenBao, OpenFGA and Keycloak in `.env`, because Veyntora needs them before anyone can sign in. Every other service is already set up in the admin console. Admins asked to connect these six from the browser too.

Two constraints make this harder than the other services:

- **They can't be stored in PostgreSQL.** Veyntora needs these settings to reach PostgreSQL in the first place.
- **OpenBao tokens are separated by role (ADR 0004).** The API token may write keys but never read them, and only the runtime services hold a token that reads them. That separation has to hold.

## Decision

**First start: the Setup page (`/setup`).**
- Until Veyntora is set up, the API serves only the Setup page's endpoints. Every page in the web app leads to `/setup`.
- The page asks for a setup code. The API prints the code in its log (`make setup-code`), and ten wrong attempts replace it.
- The admin then enters the six services and tests each connection.
- For OpenBao, the admin enters an admin token. It is used once to write three policies and issue one token for each, and it is never stored:
  - `veyntora-api`: write-only, unchanged;
  - `veyntora-runtime`: read, unchanged;
  - `veyntora-infra-read` (new): read on `kv/data/veyntora/infra/*` only.

**Later changes: Admin → Infrastructure (platform admins only).**
- The page shows all 13 services. The seven set up elsewhere in the console are listed with their state and a link.
- Saving one of the six tests it first and writes a new version.
- Every version is kept, and any earlier one can be restored. Each change and each restore is audited.
- If a change stops Veyntora from starting, the Setup page offers going back to an earlier version, again behind the setup code.

**Where things live.** The `config` volume holds `infra.json`:
- **Addresses and user names:** in plain JSON.
- **Passwords:** in OpenBao at `kv/veyntora/infra/<name>`, written with the API token. The file records the version saved, so restoring an older file brings back the passwords it was saved with.
- **Tokens:** each OpenBao token is encrypted for the services that may hold it:
  - **Infra token:** encrypted with `VEY_CONFIG_KEY`, which every container gets.
  - **API token:** encrypted with `VEY_CONFIG_API_KEY`, which only the API and migrate get.
  - **Runtime token:** sealed with RSA-OAEP to `VEY_CONFIG_RUNTIME_PUBLIC_KEY`. The API holds only the public key, so it can seal the token when it is issued but can't open it. Only the runtime services (workers, channels, graphs) hold the private key.

The keys are in `.env`, generated by `make env`. Each container gets only the keys its role needs (compose `x-keys-*`).

**How services start: `veyntora-api launch <role> -- <command>`.** Every container runs its service through this launcher, which:
1. reads the file;
2. fetches the passwords with the infra token;
3. writes only its role's token to a private file;
4. starts the service with the full settings.

When the version changes, it restarts the service. Migrate runs `bootstrap` once per version and records the result. The other services wait until that version has been bootstrapped, and the API serves the Setup page meanwhile ("starting").

**Settings from the environment still work.** Without a config file, the launcher uses `VEY_*` from the environment as before. CI uses this through `ci-infra.yaml`, and so does Helm. In that case the Infrastructure page is read-only.

## Consequences

- **What a new install needs:** `make env`, then `make up`, then the Setup page. `.env` holds no address or password, only the keys.
- **Losing the keys:** without them the config file can't be read. Keep a copy of `.env` safe; the passwords themselves stay in OpenBao.
- **The API can read connection passwords.** It holds `VEY_CONFIG_KEY`, so it can open the infra token, which reads exactly `kv/veyntora/infra/*`. The API uses it to test a changed setting with the password in use. Provider, user and integration keys stay unreadable to the API.
- **Moving data isn't automatic.** Pointing PostgreSQL or S3 somewhere new doesn't move the data, and pointing at another OpenBao doesn't move the keys. The page says so, and a changed OpenBao address is refused unless it already holds Veyntora's passwords. See `docs/runbooks/infrastructure.md`.
- **Tokens:** they are periodic (768 h), and the launchers renew them at every start and every 12 hours. Issuing new tokens doesn't revoke the old ones; those lapse after one period without renewal.
- **Setup code and logs:** whoever can read the API's log while Veyntora is not set up can set it up. That's the same trust as access to the host.
- **New dependency:** `cryptography` is now a declared dependency. It was already installed through `pyjwt[crypto]`.
